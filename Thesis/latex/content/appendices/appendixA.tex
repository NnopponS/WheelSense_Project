โครงงานเรื่อง ``WheelSense: Prototyping Development of Smart Environment for Wheelchair User'' เป็นโครงงานต้นแบบที่พัฒนาสภาพแวดล้อมอัจฉริยะสำหรับผู้ใช้เก้าอี้รถเข็นและผู้สูงอายุในอาคาร โดยบูรณาการอุปกรณ์ตรวจวัดบนเก้าอี้รถเข็น อุปกรณ์สวมใส่ แอปพลิเคชันบนอุปกรณ์เคลื่อนที่ที่ทำหน้าที่เป็น gateway, edge server, dashboard และ AI/MCP pipeline เพื่อสนับสนุนการติดตามตำแหน่ง การเคลื่อนไหว สัญญาณชีพเบื้องต้น และข้อมูลบริบทที่เกี่ยวข้องกับงานดูแล โครงงานนี้อยู่ในระดับระบบต้นแบบและมุ่งประเมินความเป็นไปได้ทางวิศวกรรม ไม่ใช่อุปกรณ์ทางการแพทย์ที่ผ่านการรับรอง \wspageref{17--21, 39--65}

\section{ปัญหาทางวิศวกรรมที่ซับซ้อน (IEA Complex Engineering Problems)}

\noindent\wschecked WP 1: ความลึกของความรู้ (Depth of knowledge)
\begin{itemize}
    \item โครงงานต้องบูรณาการความรู้ด้าน embedded system, IoT, BLE, IMU signal processing, indoor localization, backend system, dashboard และ AI/MCP pipeline เข้าด้วยกันเป็นระบบเดียว \wspageref{22--37, 39--65}
    \item การคำนวณระยะทาง ความเร็ว ความเร่ง และ motion state ต้องอาศัยทั้งการตั้งค่าอุปกรณ์จริง การกรองสัญญาณจาก sensor และการตีความข้อมูลตามบริบทของเก้าอี้รถเข็น \wspageref{31--32, 43--45, 68--71}
    \item การออกแบบระบบต้องเชื่อมข้อมูลจากอุปกรณ์ภาคสนามเข้ากับฐานข้อมูลและหน้าจอผู้ใช้ โดยยังคงตรวจสอบที่มาของข้อมูล สถานะอุปกรณ์ และความถูกต้องของ payload ได้ \wspageref{39--65}
\end{itemize}

\noindent\wschecked WP 2: ข้อกำหนดที่ขัดแย้งกัน (Range of conflicting requirements)
\begin{itemize}
    \item ระบบต้องรักษาสมดุลระหว่างความละเอียดของข้อมูลกับข้อจำกัดของอุปกรณ์ภาคสนาม เช่น battery, BLE stability, bandwidth และกำลังประมวลผลของอุปกรณ์ขนาดเล็ก \wspageref{23--28, 40--48}
    \item Dashboard ต้องแสดงข้อมูลให้ผู้ใช้แต่ละบทบาทเข้าใจได้ง่าย แต่ในขณะเดียวกันต้องจำกัดสิทธิ์การเข้าถึงข้อมูลตามบทบาทและไม่เปิดเผยข้อมูลส่วนบุคคลเกินความจำเป็น \wspageref{56--58, 79--88}
    \item AI ต้องให้คำตอบที่มีบริบทเพียงพอสำหรับช่วยผู้ดูแล แต่ต้องไม่ข้ามขั้นตอนการยืนยันของมนุษย์เมื่อเป็นคำสั่งที่เปลี่ยนสถานะระบบหรือเกี่ยวข้องกับข้อมูลผู้พักอาศัย \wspageref{58--64, 89--91}
\end{itemize}

\noindent\wschecked WP 3: ความลึกของการวิเคราะห์ (Depth of analysis)
\begin{itemize}
    \item ต้องวิเคราะห์ข้อมูลตั้งแต่ sensor, mobile gateway, MQTT/REST, database, dashboard จนถึง AI pipeline เพื่อหาจุดที่ทำให้ข้อมูลล่าช้า ขาดหาย หรือแสดงผลผิดบริบท \wspageref{39--65, 67--92}
    \item การประเมินผลในบทที่ 4 แยกการวิเคราะห์ตาม subsystem ได้แก่ sensor, indoor localization, gateway/server, dashboard/HMI และ AI/MCP เพื่อให้เห็นข้อจำกัดของแต่ละส่วนอย่างชัดเจน \wspageref{67--92}
    \item การวิเคราะห์ไม่ได้ดูเฉพาะผลลัพธ์สุดท้าย แต่ตรวจทั้งความถูกต้องของ sensor, ความเสถียรของการส่งข้อมูล, latency ของระบบ และความสอดคล้องของคำตอบจาก AI กับข้อมูลที่ระบบมีอยู่ \wspageref{68--91}
\end{itemize}

\noindent\wschecked WP 4: ความคุ้นเคยกับปัญหา (Familiarity of issues)
\begin{itemize}
    \item ปัญหาไม่ได้เป็นการทำ dashboard หรือระบบ sensor แบบแยกส่วนเท่านั้น แต่ต้องเชื่อมบริบทผู้ใช้เก้าอี้รถเข็น งานดูแลผู้สูงอายุ และระบบซอฟต์แวร์หลายชั้นเข้าด้วยกัน \wspageref{39--65}
    \item การออกแบบต้องคำนึงถึงการใช้งานของผู้ดูแลในสถานการณ์จริง เช่น การดู alert, การตรวจตำแหน่งผู้พักอาศัย, การตรวจสถานะอุปกรณ์ และการยืนยันคำสั่งก่อนให้ระบบดำเนินการ \wspageref{56--58, 79--88}
    \item ความคุ้นเคยกับปัญหาจึงต้องเกิดจากการทดสอบกับระบบต้นแบบ การพิจารณา workflow ของผู้ใช้ และการปรับขอบเขตตามข้อจำกัดที่พบระหว่างพัฒนา ไม่ใช่การนำแบบสำเร็จรูปมาใช้โดยตรง \wspageref{63--65, 93--97}
\end{itemize}

\noindent\wschecked WP 5: ขอบเขตของมาตรฐาน (Extent of applicable codes)
\begin{itemize}
    \item โครงงานต้องอ้างอิงแนวทางและมาตรฐานหลายส่วนร่วมกัน ได้แก่ BLE communication สำหรับการเชื่อมต่ออุปกรณ์ระยะใกล้, MQTT สำหรับ telemetry, REST API สำหรับ backend และ RBAC สำหรับการจำกัดสิทธิ์ผู้ใช้ \wspageref{23--28, 50--64}
    \item ข้อมูลสัญญาณชีพและข้อมูลพฤติกรรมการเคลื่อนไหวต้องถูกจัดการภายใต้หลักการลดการเข้าถึงเกินความจำเป็น การกำหนดสิทธิ์ตามบทบาท และการเก็บหลักฐานการทำงานที่ตรวจสอบย้อนหลังได้ \wspageref{56--64}
    \item เนื่องจากระบบเป็นต้นแบบและไม่ใช่อุปกรณ์ทางการแพทย์ที่ผ่านการรับรอง จึงต้องกำหนดขอบเขตการใช้งานให้ชัดเจน และไม่ใช้ผลจากระบบแทนการประเมินของบุคลากรทางการแพทย์ \wspageref{22--24, 95--97}
\end{itemize}

\noindent\wschecked WP 6: ผู้มีส่วนได้ส่วนเสีย (Extent of stakeholder involvement and needs)
\begin{itemize}
    \item ผู้ใช้แต่ละบทบาทมีความต้องการต่างกัน เช่น ผู้พักอาศัยต้องเห็นข้อมูลของตนเอง ผู้ดูแลต้องเห็น alert และหัวหน้าพยาบาลต้องเห็นภาพรวมของงานดูแล \wspageref{56--58, 79--88}
    \item ผู้บริหารสถานดูแลต้องการข้อมูลภาพรวมและเหตุการณ์ย้อนหลังเพื่อประกอบการจัดสรรทรัพยากร ส่วนทีมพัฒนาต้องการ log และสถานะระบบเพื่อวิเคราะห์ปัญหาเมื่อข้อมูลขาดหายหรือบริการหยุดทำงาน \wspageref{93--97}
    \item การออกแบบจึงต้องแยกสิทธิ์ หน้าจอ และข้อมูลที่แสดงตามบทบาทผู้ใช้ เพื่อให้ระบบตอบโจทย์ผู้มีส่วนได้ส่วนเสียหลายกลุ่มโดยไม่ทำให้ข้อมูลส่วนบุคคลถูกเปิดเผยเกินจำเป็น \wspageref{56--58, 79--88}
\end{itemize}

\noindent\wschecked WP 7: ความเกี่ยวพันของระบบ (Interdependence)
\begin{itemize}
    \item Sensor, mobile gateway, backend, database, dashboard และ AI/MCP เชื่อมต่อกันเป็นลำดับ หากส่วนใดส่วนหนึ่งขัดข้องจะกระทบต่อการเห็นสถานะของผู้ดูแล \wspageref{39--65}
    \item Execution Gate ถูกออกแบบให้คั่นระหว่างคำตอบของ AI กับการสั่งงานจริง เพื่อให้การเปลี่ยนสถานะต้องผ่านการตรวจสอบก่อนดำเนินการ \wspageref{58--64, 89--91}
    \item การทดสอบระบบจึงต้องตรวจทั้งการทำงานรายส่วนและการเชื่อมต่อข้ามส่วน เช่น BLE ไปยัง mobile gateway, gateway ไปยัง server, server ไปยัง dashboard และข้อมูลบริบทที่ AI เรียกใช้ \wspageref{63--65, 67--92}
\end{itemize}

\section{องค์ความรู้และเครื่องมืออุปกรณ์ที่ใช้}

\subsection*{องค์ความรู้ทางวิศวกรรม}
\begin{itemize}
    \item การประมวลผลสัญญาณจาก IMU สำหรับ motion magnitude, velocity, distance และ acceleration ของเก้าอี้รถเข็น \wspageref{31--32, 43--45, 68--71}
    \item การระบุตำแหน่งภายในอาคารด้วย BLE RSSI, fingerprinting, KNN และ max-RSSI baseline \wspageref{29--30, 47--50, 72--74}
    \item ระบบ IoT และ message flow ผ่าน BLE, MQTT, REST API, WebSocket และ database \wspageref{23--28, 40--55, 75--78}
    \item การออกแบบ backend และฐานข้อมูลสำหรับ telemetry, event, alert, audit log และข้อมูลผู้ใช้ตามบทบาท \wspageref{50--55, 75--78, 125--128}
    \item การออกแบบ AI pipeline แบบแยกชั้น ได้แก่ Intent Router, Context Assembler, Behavioral State, Constrained LLM และ Execution Gate \wspageref{34--36, 58--64, 89--91}
\end{itemize}

\subsection*{องค์ความรู้ทางสาขาอื่น}
\begin{itemize}
    \item แนวคิดด้านการดูแลผู้สูงอายุและผู้ใช้เก้าอี้รถเข็นในสถานดูแล ซึ่งต้องคำนึงถึงตำแหน่ง การเคลื่อนไหว การขอความช่วยเหลือ และภาระงานของผู้ดูแล \wspageref{17--23}
    \item หลักการออกแบบ Human--Machine Interface (HMI) และ usability สำหรับผู้ใช้หลายบทบาท เช่น Admin, Head Nurse, Supervisor, Observer และ Patient \wspageref{56--58, 79--88, 121}
    \item แนวคิดด้านข้อมูลส่วนบุคคลและจริยธรรมในการจัดการข้อมูลสุขภาพเบื้องต้น โดยจำกัดการเข้าถึงตามความจำเป็นและบทบาทของผู้ใช้ \wspageref{19, 56--64, 95--97}
    \item การบริหารงานในสถานดูแล เช่น การมอบหมายงาน การติดตามเหตุการณ์ การส่งต่อเวร และการตรวจสอบเหตุการณ์ย้อนหลัง \wspageref{56--58, 79--88, 93--97}
\end{itemize}

\subsection*{โปรแกรมหรือเครื่องมือสมัยใหม่}
\begin{itemize}
    \item M5StickC Plus2 สำหรับอ่านข้อมูล IMU, battery และส่ง telemetry จากเก้าอี้รถเข็น \wspageref{24--27, 43--45, 68--71}
    \item Polar Verity Sense สำหรับข้อมูล heart rate, RR interval และ PPG ในระดับต้นแบบ \wspageref{24--27, 46--48, 75--76, 111}
    \item Flutter mobile gateway สำหรับรวมข้อมูลจากอุปกรณ์ภาคสนามและส่งข้อมูลไปยัง server \wspageref{27--28, 46--48, 75--76, 127}
    \item Raspberry Pi 5, Docker Compose, FastAPI, PostgreSQL/JSONB และ MQTT broker สำหรับ edge/server runtime \wspageref{24--28, 50--55, 75--78, 125--128}
    \item Next.js dashboard สำหรับแสดงผลตามบทบาทผู้ใช้ และ EaseAI/MCP สำหรับช่วยค้นบริบท สรุปข้อมูล และเตรียม action candidate \wspageref{27--28, 56--64, 79--91, 121}
    \item PlatformIO, Flutter test, Jest/Playwright และชุดทดสอบ backend สำหรับตรวจการ build, unit test และ end-to-end workflow ของระบบ \wspageref{63--65, 67--92}
\end{itemize}

\section{มาตรฐาน กฎหมาย และข้อบังคับที่เกี่ยวข้อง}

\subsection*{มาตรฐานทางวิศวกรรม}
\begin{itemize}
    \item BLE communication ใช้เป็นพื้นฐานของการเชื่อมต่ออุปกรณ์ระยะใกล้ระหว่าง sensor และ mobile gateway \wspageref{23--24, 40--48}
    \item MQTT ใช้เป็นแนวทางการส่ง telemetry แบบ lightweight ระหว่าง gateway และ server \wspageref{23--24, 50--55, 75--78}
    \item REST API และ JSON schema ใช้กำหนดรูปแบบข้อมูลระหว่าง frontend, backend และ AI/MCP tool contract \wspageref{27--28, 50--55, 113--119}
    \item RBAC, audit trail และ session security ใช้จำกัดการเข้าถึงข้อมูลตามบทบาทผู้ใช้และตรวจสอบการดำเนินการย้อนหลัง \wspageref{56--64, 79--88}
\end{itemize}

\subsection*{มาตรฐานทางสาขาอื่น}
\begin{itemize}
    \item แนวทาง Ambient Assisted Living (AAL) และ smart care environment ใช้เป็นกรอบการออกแบบระบบช่วยดูแลที่ไม่แทนที่การตัดสินใจของผู้ดูแล \wspageref{17--23}
    \item แนวคิด usability และแบบประเมิน System Usability Scale (SUS) ใช้ประกอบการประเมินประสบการณ์ใช้งานของ dashboard ตามบทบาทผู้ใช้ \wspageref{79--88, 121}
    \item หลักการ human-in-the-loop ใช้กับ AI/MCP pipeline เพื่อให้คำสั่งที่กระทบต่อระบบจริงต้องผ่านการตรวจสอบและยืนยันจากผู้ใช้ก่อนเสมอ \wspageref{58--64, 89--91}
\end{itemize}

\subsection*{กฎหมายหรือข้อบังคับ}
\begin{itemize}
    \item การจัดการข้อมูลผู้พักอาศัย ข้อมูลสัญญาณชีพ และข้อมูลพฤติกรรมการเคลื่อนไหวควรสอดคล้องกับหลักการคุ้มครองข้อมูลส่วนบุคคล โดยกำหนดวัตถุประสงค์และสิทธิ์การเข้าถึงให้ชัดเจน \wspageref{19, 56--64}
    \item การทดสอบกับผู้ใช้จริงในอนาคตควรมีกระบวนการขอความยินยอม การชี้แจงขอบเขตการใช้ข้อมูล และการจัดการข้อมูลที่สามารถระบุตัวบุคคลได้ \wspageref{95--97}
    \item อุปกรณ์สื่อสารไร้สายและอุปกรณ์ไฟฟ้าที่นำไปใช้ในสภาพแวดล้อมจริงควรเลือกใช้อุปกรณ์ที่ผ่านข้อกำหนดความปลอดภัยและข้อกำหนดการสื่อสารที่เกี่ยวข้อง \wspageref{23--27, 40--48}
\end{itemize}

\subsection*{ข้อบังคับความปลอดภัยหรือสิ่งแวดล้อม}
\begin{itemize}
    \item การติดตั้ง sensor บนเก้าอี้รถเข็นต้องไม่รบกวนการใช้งานเดิม ไม่ทำให้เกิดจุดเกี่ยว สะดุด หรือเพิ่มความเสี่ยงต่อผู้ใช้ \wspageref{43--45, 68--71}
    \item อุปกรณ์ที่มีแบตเตอรี่ควรมีแนวทางการชาร์จ การถอดเปลี่ยน และการตรวจสภาพเพื่อลดความเสี่ยงจากความร้อนหรือการเสื่อมสภาพของแบตเตอรี่ \wspageref{24--27, 43--45, 95--97}
    \item ระบบต้นแบบไม่ใช่อุปกรณ์ทางการแพทย์ที่ผ่านการรับรอง จึงต้องแสดงขอบเขตการใช้งานให้ชัดเจนและไม่ใช้ผลจากระบบแทนการประเมินจากบุคลากรทางการแพทย์ \wspageref{22--24, 95--97}
    \item เมื่อพัฒนาต่อยอดควรวางแนวทางจัดการซากอุปกรณ์อิเล็กทรอนิกส์และแบตเตอรี่ เพื่อลดผลกระทบด้านขยะอิเล็กทรอนิกส์ \wspageref{95--97}
\end{itemize}

\section{ผู้มีส่วนได้ส่วนเสีย ผลกระทบ และความยั่งยืน}

\subsection*{กลุ่มผู้มีส่วนได้ส่วนเสีย (Stakeholders)}
\begin{itemize}
    \item ผู้ใช้เก้าอี้รถเข็นและผู้สูงอายุ เป็นกลุ่มที่ได้รับผลโดยตรงจากการติดตามตำแหน่ง การเคลื่อนไหว และสถานะเบื้องต้น \wspageref{17--22}
    \item ผู้ดูแลและหัวหน้าพยาบาล ใช้ dashboard, alert, task และข้อมูลบริบทเพื่อช่วยจัดลำดับงานดูแลและติดตามเหตุการณ์ในแต่ละช่วงเวลา \wspageref{56--58, 79--88}
    \item ผู้บริหารสถานดูแล ใช้ข้อมูลภาพรวมและเหตุการณ์ย้อนหลังเพื่อประกอบการวางแผนทรัพยากร บุคลากร และกระบวนการดูแล \wspageref{93--97}
    \item ผู้ดูแลระบบและทีมพัฒนา รับผิดชอบความถูกต้องของข้อมูล การบำรุงรักษาอุปกรณ์ การจัดการสิทธิ์ และการตรวจสอบ log เมื่อระบบมีปัญหา \wspageref{50--64, 75--78}
    \item อาจารย์ที่ปรึกษาและผู้เชี่ยวชาญที่ให้ข้อเสนอแนะ ใช้ข้อมูลจากการทดสอบเพื่อประเมินความเหมาะสมของแนวทางและข้อจำกัดของระบบต้นแบบ \wspageref{17--21, 63--65}
\end{itemize}

\subsection*{ผลกระทบของโครงงาน (ต่อสังคม/เศรษฐกิจ/สิ่งแวดล้อม)}
\begin{itemize}
    \item สังคม (ด้านบวก): ช่วยให้ผู้ดูแลเห็นข้อมูลตำแหน่ง สถานะ และ alert จากจุดศูนย์กลาง ลดการค้นหาข้อมูลจากหลายแหล่ง และช่วยให้การส่งต่อข้อมูลระหว่างผู้ดูแลเป็นระบบมากขึ้น \wspageref{17--20, 79--88, 93--95}
    \item สังคม (ด้านลบ): หากกำหนดสิทธิ์หรือขอบเขตการใช้ข้อมูลไม่ชัดเจน อาจทำให้เกิดความเสี่ยงด้านความเป็นส่วนตัว หรือทำให้ผู้ใช้ตีความข้อมูลจากระบบเกินกว่าระดับต้นแบบ \wspageref{19, 56--64, 95--97}
    \item เศรษฐกิจ (ด้านบวก): ต้นแบบใช้ hardware และ open-source software ที่หาได้ทั่วไป จึงเหมาะกับการทดลอง พัฒนาต่อยอด และปรับใช้ในขอบเขตที่ควบคุมต้นทุนได้ \wspageref{24--28, 93--97}
    \item เศรษฐกิจ (ด้านลบ): การนำไปใช้งานจริงยังต้องคำนึงถึงค่าใช้จ่ายด้านการบำรุงรักษา อุปกรณ์สำรอง การฝึกอบรมผู้ใช้ และเวลาในการดูแลระบบ \wspageref{95--97}
    \item สิ่งแวดล้อม (ด้านบวก): การใช้ edge server ภายในพื้นที่ช่วยลดการพึ่งพา cloud ภายนอกบางส่วน และเปิดโอกาสให้ควบคุมอุปกรณ์เฉพาะจุดตามความจำเป็นของต้นแบบ \wspageref{24--28, 50--55, 95--97}
    \item สิ่งแวดล้อม (ด้านลบ): อุปกรณ์อิเล็กทรอนิกส์ แบตเตอรี่ และ sensor ที่เสื่อมสภาพอาจกลายเป็นขยะอิเล็กทรอนิกส์ จึงควรวางแผนการถอดเปลี่ยนและกำจัดอย่างเหมาะสม \wspageref{95--97}
\end{itemize}

\subsection*{ความเกี่ยวข้องกับเป้าหมายการพัฒนาที่ยั่งยืน (SDGs)}
\begin{itemize}
    \item SDG 3: สุขภาพและความเป็นอยู่ที่ดี โครงงานสนับสนุนการเฝ้าระวังเบื้องต้นและการจัดการข้อมูลดูแลผู้สูงอายุหรือผู้ใช้เก้าอี้รถเข็นในระดับต้นแบบ \wspageref{17--20, 93--95}
    \item SDG 9: อุตสาหกรรม นวัตกรรม และโครงสร้างพื้นฐาน โครงงานพัฒนาโครงสร้างพื้นฐานด้าน IoT, edge computing, dashboard และ AI tool workflow สำหรับสถานดูแล \wspageref{39--65, 93--95}
    \item SDG 10: ลดความเหลื่อมล้ำ โครงงานมุ่งลดอุปสรรคในการเข้าถึงข้อมูลดูแลสำหรับผู้ใช้เก้าอี้รถเข็นและผู้สูงอายุ โดยยังต้องคำนึงถึงสิทธิ์และความเป็นส่วนตัวของผู้ใช้ \wspageref{17--20, 95--97}
    \item SDG 11: เมืองและชุมชนที่ยั่งยืน โครงงานมีแนวทางต่อยอดสู่สภาพแวดล้อมอัจฉริยะในอาคารที่ช่วยให้พื้นที่ดูแลมีข้อมูลประกอบการจัดการมากขึ้น \wspageref{39--65, 97}
\end{itemize}

\section{การบริหารงานวิศวกรรมและโครงการ}

\subsection*{การบริหารบุคคล}
\begin{itemize}
    \item คณะผู้จัดทำมี 2 คน แบ่งงานตามความถนัดและ subsystem ของโครงงาน ได้แก่ sensor/firmware, mobile gateway, backend/server, dashboard/HMI และ AI/MCP pipeline \wspageref{17--21, 63--65}
    \item งานที่เกี่ยวข้องกันถูกประสานผ่านการกำหนด schema, API contract, MQTT topic และสิทธิ์การเข้าถึง เพื่อให้แต่ละส่วนพัฒนาแยกกันได้แต่ยังเชื่อมต่อกันเป็นระบบเดียว \wspageref{50--64, 113--119}
    \item มีการปรึกษาอาจารย์ที่ปรึกษาและผู้ให้ข้อมูลจากบริบทการใช้งานจริง เพื่อปรับขอบเขตงานให้เหมาะสมกับเวลา อุปกรณ์ และหลักฐานที่สามารถทดสอบได้ \wspageref{17--21, 63--65}
\end{itemize}

\subsection*{การบริหารเวลา}
\begin{itemize}
    \item การดำเนินงานแบ่งเป็นช่วงศึกษาเอกสาร วิเคราะห์ปัญหา ออกแบบระบบ พัฒนาอุปกรณ์และซอฟต์แวร์ บูรณาการ ทดสอบ และจัดทำเล่มรายงาน \wspageref{21}
    \item ใช้การทดสอบรายส่วนก่อนการทดสอบรวมระบบ เช่น firmware build, mobile gateway test, backend test, dashboard test และ AI/MCP test เพื่อลดความเสี่ยงจากการแก้ไขหลายส่วนพร้อมกัน \wspageref{63--65, 67--92}
    \item เมื่อพบข้อจำกัดระหว่างพัฒนา เช่น BLE/RSSI fluctuation, latency ของ AI หรือความไม่ครบของข้อมูล telemetry จะปรับลำดับงานให้แก้ส่วนที่กระทบต่อการทดลองก่อน \wspageref{95--97}
\end{itemize}

\subsection*{การบริหารงบประมาณ/ทรัพยากร}
\begin{itemize}
    \item ทรัพยากรหลักประกอบด้วย M5StickC Plus2, Polar Verity Sense, Raspberry Pi 5, โทรศัพท์สำหรับ gateway, เก้าอี้รถเข็นสำหรับติดตั้งทดสอบ และเครื่องมือซอฟต์แวร์ที่ใช้พัฒนา \wspageref{24--28}
    \item เลือกใช้ open-source software และอุปกรณ์ที่หาได้ทั่วไป เช่น FastAPI, PostgreSQL, Docker Compose, Flutter และ Next.js เพื่อลดต้นทุนการทดลองและทำให้ระบบทำซ้ำได้ง่ายขึ้น \wspageref{27--28}
    \item การบริหารทรัพยากรเน้นให้แต่ละอุปกรณ์มีบทบาทชัดเจน เช่น M5StickC Plus2 เป็น wheelchair sensor, Polar Verity Sense เป็น wearable sensor และ Raspberry Pi 5 เป็น edge/local server \wspageref{24--28, 43--55}
    \item ในการพัฒนาต่อควรจัดทำรายการค่าใช้จ่ายจริง ค่าอุปกรณ์สำรอง และค่าใช้จ่ายด้านบำรุงรักษา เพื่อประเมินความเหมาะสมก่อนนำไปใช้ในสภาพแวดล้อมจริง \wspageref{95--97}
\end{itemize}

\subsection*{การบริหารความเสี่ยง}
\begin{itemize}
    \item ความเสี่ยงด้าน BLE/RSSI fluctuation และ sensor noise ถูกจัดการด้วยการทดสอบซ้ำ การใช้ baseline หลายแบบ และการแยกผลการประเมินตาม subsystem \wspageref{29--32, 68--74}
    \item ความเสี่ยงด้านข้อมูลขาดหายหรือข้อมูลมาช้าถูกลดลงด้วยการแยก gateway, backend, database และ dashboard เป็นชั้นการทำงานที่ตรวจสอบ log และสถานะได้ \wspageref{75--78}
    \item ความเสี่ยงจากการสั่งงานของ AI ลดลงด้วยแนวทาง Propose--Confirm--Execute เพื่อให้ผู้ดูแลตรวจสอบก่อนดำเนินการจริง \wspageref{58--64, 89--91}
    \item ความเสี่ยงด้านความเป็นส่วนตัวถูกลดลงด้วย RBAC, session control, audit trail และการแสดงข้อมูลตามบทบาทผู้ใช้ \wspageref{56--64, 95--97}
    \item ความเสี่ยงด้านการใช้งานจริงยังคงต้องประเมินเพิ่มเติมในอนาคต เช่น ความทนทานของอุปกรณ์ การฝึกผู้ใช้ การดูแลแบตเตอรี่ และการกำหนดกระบวนการขอความยินยอมจากผู้ใช้จริง \wspageref{95--97}
\end{itemize}
