\newcommand{\wsunchecked}{\makebox[1.4em][l]{\ensuremath{\square}}}

โครงงานเรื่อง ``WheelSense: Prototyping Development of Smart Environment for Wheelchair User'' เป็นโครงงานต้นแบบที่บูรณาการอุปกรณ์ตรวจวัดบนเก้าอี้รถเข็น อุปกรณ์สวมใส่ โทรศัพท์มือถือที่ทำหน้าที่เป็น gateway, edge server, dashboard และ AI/MCP pipeline เพื่อสนับสนุนการติดตามสถานะผู้ใช้เก้าอี้รถเข็นและผู้สูงอายุในสภาพแวดล้อมภายในอาคาร

\section{ปัญหาทางวิศวกรรมที่ซับซ้อน}

\noindent\wschecked WP 1: ความลึกของความรู้ (Depth of knowledge)
\begin{itemize}
    \item โครงงานต้องบูรณาการความรู้ด้าน embedded system, IoT, BLE, IMU signal processing, indoor localization, backend system, dashboard และ AI/MCP pipeline เข้าด้วยกันเป็นระบบเดียว
    \item การคำนวณระยะทาง ความเร็ว ความเร่ง และ motion state ต้องอาศัยทั้งการตั้งค่าอุปกรณ์จริงและการกรองสัญญาณจากข้อมูล sensor
\end{itemize}

\noindent\wschecked WP 2: ข้อกำหนดที่ขัดแย้งกัน (Range of conflicting requirements)
\begin{itemize}
    \item ระบบต้องรักษาสมดุลระหว่างความละเอียดของข้อมูลกับข้อจำกัดของอุปกรณ์ภาคสนาม เช่น battery, BLE stability และ bandwidth
    \item AI ต้องให้คำตอบที่มีบริบทเพียงพอ แต่ต้องไม่ข้ามขั้นตอนการยืนยันของผู้ดูแลเมื่อเป็นคำสั่งที่เปลี่ยนสถานะระบบ
\end{itemize}

\noindent\wschecked WP 3: ความลึกของการวิเคราะห์ (Depth of analysis)
\begin{itemize}
    \item ต้องวิเคราะห์ข้อมูลตั้งแต่ sensor, mobile gateway, MQTT/REST, database, dashboard จนถึง AI pipeline เพื่อหาจุดที่ทำให้ข้อมูลล่าช้า ขาดหาย หรือแสดงผลผิดบริบท
    \item ผลการทดลองในบทที่ 4 แยกการวิเคราะห์ตาม subsystem เพื่อให้เห็นข้อจำกัดของแต่ละส่วนอย่างชัดเจน
\end{itemize}

\noindent\wsunchecked WP 4: ความคุ้นเคยกับปัญหา (Familiarity of issues)
\begin{itemize}
    \item ไม่ใช่ปัญหาซ้ำรูปแบบตรงไปตรงมา เพราะต้องเชื่อมบริบทผู้ใช้เก้าอี้รถเข็น งานดูแลผู้สูงอายุ และระบบซอฟต์แวร์หลายชั้นเข้าด้วยกัน
\end{itemize}

\noindent\wsunchecked WP 5: ขอบเขตของมาตรฐาน (Extent of applicable codes)
\begin{itemize}
    \item ยังไม่มีมาตรฐานเดียวที่ครอบคลุมทั้ง BLE sensor, indoor localization, dashboard care workflow และ AI tool execution ในโครงงานต้นแบบนี้
\end{itemize}

\noindent\wsunchecked WP 6: ผู้มีส่วนได้ส่วนเสีย (Extent of stakeholder involvement and needs)
\begin{itemize}
    \item ผู้ใช้แต่ละบทบาทมีความต้องการต่างกัน เช่น ผู้พักอาศัยต้องเห็นข้อมูลส่วนตัว ผู้ดูแลต้องเห็น alert และหัวหน้าพยาบาลต้องเห็นภาพรวมของงานดูแล
\end{itemize}

\noindent\wschecked WP 7: ความเกี่ยวพันของระบบ (Interdependence)
\begin{itemize}
    \item Sensor, mobile gateway, backend, database, dashboard และ AI/MCP เชื่อมต่อกันเป็นลำดับ หากส่วนใดส่วนหนึ่งขัดข้องจะกระทบต่อการเห็นสถานะของผู้ดูแล
    \item Execution Gate ถูกออกแบบให้คั่นระหว่างคำตอบของ AI กับการสั่งงานจริง เพื่อให้การเปลี่ยนสถานะต้องผ่านการตรวจสอบก่อนดำเนินการ
\end{itemize}

\section{องค์ความรู้และเครื่องมืออุปกรณ์ที่ใช้}

\subsection*{องค์ความรู้ทางวิศวกรรม}
\begin{itemize}
    \item การประมวลผลสัญญาณจาก IMU สำหรับ motion magnitude, velocity, distance และ acceleration
    \item การระบุตำแหน่งภายในอาคารด้วย BLE RSSI, fingerprinting, KNN และ max-RSSI baseline
    \item ระบบ IoT และ message flow ผ่าน BLE, MQTT, REST API และ database
    \item การออกแบบ AI pipeline แบบแยกชั้น ได้แก่ Intent Router, Context Assembler, Behavioral State, Constrained LLM และ Execution Gate
\end{itemize}

\subsection*{เครื่องมือและอุปกรณ์หลัก}
\begin{itemize}
    \item M5StickC Plus2 สำหรับอ่านข้อมูล IMU และส่ง telemetry จากเก้าอี้รถเข็น
    \item Polar Verity Sense สำหรับข้อมูลสัญญาณชีพในระดับต้นแบบ
    \item Flutter mobile gateway สำหรับรวมข้อมูลจากอุปกรณ์ภาคสนามและส่งข้อมูลไปยัง server
    \item Raspberry Pi 5, Docker, FastAPI, PostgreSQL/JSONB และ MQTT broker สำหรับ edge/server runtime
    \item Next.js dashboard สำหรับแสดงผลตามบทบาทผู้ใช้ และ EaseAI/MCP สำหรับช่วยค้นบริบทและเตรียม action candidate
\end{itemize}

\section{มาตรฐาน กฎหมาย และข้อบังคับที่เกี่ยวข้อง}

\subsection*{มาตรฐานทางวิศวกรรม}
\begin{itemize}
    \item BLE communication ใช้เป็นพื้นฐานของการเชื่อมต่ออุปกรณ์ระยะใกล้ระหว่าง sensor และ mobile gateway
    \item MQTT ใช้เป็นแนวทางการส่ง telemetry แบบ lightweight ระหว่าง gateway และ server
    \item Role-based access control และ audit trail ใช้จำกัดการเข้าถึงข้อมูลตามบทบาทผู้ใช้
\end{itemize}

\subsection*{ข้อพิจารณาด้านกฎหมายและจริยธรรม}
\begin{itemize}
    \item ข้อมูลสัญญาณชีพและข้อมูลพฤติกรรมการเคลื่อนไหวควรถูกจำกัดการเข้าถึงเฉพาะบทบาทที่เกี่ยวข้อง
    \item ระบบต้นแบบนี้ไม่ใช่อุปกรณ์ทางการแพทย์ที่ผ่านการรับรอง และไม่ควรถูกใช้แทนการประเมินจากบุคลากรทางการแพทย์
    \item การทดสอบกับผู้ใช้จริงในอนาคตควรมีกระบวนการขอความยินยอม การจัดการข้อมูลส่วนบุคคล และการกำหนดขอบเขตการใช้ข้อมูลอย่างชัดเจน
\end{itemize}

\section{ผู้มีส่วนได้ส่วนเสีย ผลกระทบ และความยั่งยืน}

\subsection*{ผู้มีส่วนได้ส่วนเสีย}
\begin{itemize}
    \item ผู้ใช้เก้าอี้รถเข็นและผู้สูงอายุ เป็นผู้ที่ได้รับผลจากการติดตามตำแหน่ง การเคลื่อนไหว และสถานะเบื้องต้น
    \item ผู้ดูแลและหัวหน้าพยาบาล ใช้ dashboard, alert และข้อมูลบริบทเพื่อช่วยจัดลำดับงานดูแล
    \item ผู้บริหารสถานดูแล ใช้ข้อมูลภาพรวมเพื่อประกอบการวางแผนทรัพยากรและติดตามเหตุการณ์ย้อนหลัง
    \item ทีมพัฒนาและผู้ดูแลระบบ รับผิดชอบความถูกต้องของข้อมูล การบำรุงรักษาระบบ และการควบคุมสิทธิ์การเข้าถึง
\end{itemize}

\subsection*{ผลกระทบและความยั่งยืน}
\begin{itemize}
    \item ด้านสังคม: ช่วยให้ผู้ดูแลเห็นข้อมูลตำแหน่ง สถานะ และ alert จากจุดศูนย์กลาง ลดการค้นหาข้อมูลจากหลายแหล่ง
    \item ด้านเศรษฐกิจ: ต้นแบบใช้ hardware และ open-source software ที่หาได้ทั่วไป จึงเหมาะกับการทดลองและพัฒนาต่อโดยควบคุมต้นทุน
    \item ด้านสิ่งแวดล้อม: อุปกรณ์อิเล็กทรอนิกส์และแบตเตอรี่ควรถูกออกแบบให้ถอดเปลี่ยนและจัดการซากอุปกรณ์ได้อย่างเหมาะสม
    \item ความเชื่อมโยงกับ SDGs: โครงงานเกี่ยวข้องกับสุขภาพและความเป็นอยู่ที่ดี นวัตกรรมโครงสร้างพื้นฐาน และการลดอุปสรรคในการดูแลผู้สูงอายุหรือผู้ใช้เก้าอี้รถเข็น
\end{itemize}

\section{การบริหารงานวิศวกรรมและโครงการ}

\subsection*{การแบ่งงานและการติดตาม}
\begin{itemize}
    \item แบ่งงานตาม subsystem ได้แก่ sensor/firmware, mobile gateway, backend/server, dashboard/HMI และ AI/MCP pipeline
    \item ใช้การทดสอบรายส่วนและการทดสอบการเชื่อมต่อระบบเพื่อตรวจความพร้อมก่อนรวบรวมผลในบทที่ 4
    \item ติดตามความคืบหน้าด้วยการประชุมกับอาจารย์ที่ปรึกษาและการปรับขอบเขตตามข้อจำกัดที่พบระหว่างพัฒนา
\end{itemize}

\subsection*{การบริหารทรัพยากรและความเสี่ยง}
\begin{itemize}
    \item ทรัพยากรหลักประกอบด้วย M5StickC Plus2, Polar Verity Sense, Raspberry Pi 5, โทรศัพท์สำหรับ gateway และเก้าอี้รถเข็นสำหรับติดตั้งทดสอบ
    \item ความเสี่ยงด้าน hardware delay, BLE/RSSI fluctuation, sensor noise และ AI latency ถูกจัดการด้วยการแบ่งระบบเป็นชั้นและมี fallback ในระดับที่เหมาะสมกับต้นแบบ
    \item ความเสี่ยงจากการสั่งงานของ AI ลดลงด้วยแนวทาง Propose--Confirm--Execute เพื่อให้ผู้ดูแลตรวจสอบก่อนดำเนินการ
\end{itemize}
