# WheelSense UI/UX Audit

Audit date: 2026-08-18  
Target: current Next.js production UI and simulator/demo control surfaces  
Method: Hallmark source audit + Impeccable v4.1.1 critique/detector + Graft call/ownership tracing  
Mode: **DEGRADED — single-context audit** (no independent sub-agent critique was authorized)  
Runtime status: **NOT VERIFIED** — Docker exposed `localhost:3000`, but the page did not respond before the browser audit timeout. No live screenshot, interaction, responsive, or computed-style result is claimed.

## Executive result

The UI has a usable visual foundation, but the UX architecture is **Poor: 18/40** in the source-based heuristic review. The user's description is accurate: the screens can look acceptable while the experience remains fragmented, duplicated, and hard to predict.

The root cause is not primarily color or styling. It is four structural problems:

1. Two operational roles represent overlapping real-world responsibility with divergent permissions and separate navigation trees.
2. Dashboard pages aggregate too many independent jobs without a clear priority path.
3. Repeated card/queue/action components encode different interaction semantics.
4. Production and simulation logic share screens without a sufficiently strict mode boundary.

## What is already good

- React Query is used consistently for server state, refresh, and mutation invalidation.
- Zod/react-hook-form are already present in complex forms.
- Clinical status colors and emergency severity are meaningful rather than decorative.
- Shared role shell, sidebar, mailbox, and API client patterns exist; the redesign can reuse them instead of creating a second frontend.
- `RoleQuickActions` includes focus-visible styling and `aria-label` support.
- Supervisor's smaller dashboard already points toward a priority queue model.
- Simulator status exists and is exposed in multiple places, so a centralized mode contract can reuse existing API data.

## Priority findings

### P0 — Separate Head Nurse and Supervisor roles conflict with one real workflow

**Tell:** duplicated role home/routes/navigation with divergent capability sets.  
**Where:**

- `frontend/lib/permissions.ts:48-81,95-100`
- `frontend/lib/sidebarConfig.ts:121-231`
- `frontend/lib/routes.ts:2-16,24-31,53-60`
- `server/app/api/dependencies.py:171-336,353-370`
- `server/app/services/ai_chat.py:231-245`
- `server/app/schemas/users.py:50-78`

**Evidence:** current Head Nurse can manage users/patients/caregivers/devices and has workspace-wide patient visibility; current Supervisor is a narrower read/alert/workflow role. The MCP allowlist explicitly derives Supervisor by subtracting tools from Head Nurse.

**Impact:** users with the same operational leadership job receive different routes, permissions, AI tools, and dashboard concepts. Merging labels without migrating authorization would either break Head Nurse workflows or silently widen Supervisor access.

**Fix:** canonicalize to `supervisor`, explicitly define the union permission matrix, retain admin-only negative cases, migrate stored roles, normalize legacy input, refresh sessions, redirect legacy routes, and test every permission before deleting any compatibility path.

### P0 — Production and simulator are not modeled as strict data adapters

**Tell:** production queries, simulator status, scenario controls, manual alerts, reset behavior, and hard-coded sample copy coexist in one page.  
**Where:** `frontend/app/admin/demo-control/page.tsx:71-460`; duplicate `SimulatorStatus` types also exist in `TopBar.tsx` and `ServerSettingsPanel.tsx`.

**Impact:** the UI can vary by scattered booleans rather than one explicit mode contract. This increases the risk of simulator controls or generated data appearing in production and encourages production/sim forks.

**Fix:** one shared view model and component tree; a production adapter and a simulator adapter; persistent Simulation banner; simulator mutation/control API available only through an admin simulator surface; production adapter must fail closed on mock data.

### P1 — Head Nurse command center is a monolithic, equal-weight dashboard

**Tell:** card-grid/default-dashboard attractor and excessive aggregation.  
**Where:** `frontend/app/head-nurse/page.tsx:125-1300`.

**Evidence:** the page owns ward summary, alerts, patients, caregivers, rooms, tasks, schedules, directives, messages, handovers, and smart devices, plus mutations and derived panels. The render includes patient attention, staff workload, task/message/handover work queues, and device/location monitoring.

**Impact:** a user beginning a shift cannot immediately answer one primary question. All operational domains compete for attention and every change risks a large page regression.

**Fix:** one Supervisor command center with this hierarchy:

1. Critical intervention queue.
2. Shift status and staffing exceptions.
3. Patients needing attention.
4. Open work and handover.
5. Device/location exceptions.
6. Secondary analytics/details behind drill-down routes or drawers.

### P1 — Supervisor has overlapping queue implementations

**Tell:** duplicate user-visible model and mutation ownership.  
**Where:**

- `frontend/components/supervisor/SupervisorQueue.tsx:51-439`
- `frontend/components/supervisor/SupervisorHealthQueue.tsx:12-158`

**Evidence:** both prioritize/operate on tasks. `SupervisorQueue` also merges alerts and directives and owns mutations; `SupervisorHealthQueue` filters “my tasks” and accepts callback mutations.

**Disconnected contract:** `SupervisorQueueProps.onItemAction` is declared but never destructured or called.

**Impact:** ordering, labels, invalidation, and ownership can drift; the optional callback implies a connection that does not exist.

**Fix:** keep one canonical queue domain model and one mutation boundary. Derive “urgent”, “mine”, and “waiting” as filters/views, not separate implementations. Remove the dead prop or wire it only if a real owner exists.

### P1 — Quick actions use identical visuals for different behavior

**Tell:** “every action is a card” plus inconsistent interaction semantics.  
**Where:**

- `frontend/components/dashboard/RoleQuickActions.tsx:50-92`
- `frontend/components/dashboard/FeatureDetailActions.tsx:23-67`

**Evidence:** a quick action with `href` navigates; an action without `href` opens an AI prompt. Feature detail actions are another visually similar route-card grid.

**Impact:** the same card affordance does not tell the user whether it will navigate, mutate, or open AI. It also duplicates the sidebar and dashboard.

**Fix:** navigation uses links/list rows with destinations; mutations use buttons with explicit verbs and pending/result state; AI suggestions are labeled “Ask EaseAI” and use a distinct treatment. Keep only shortcuts proven to reduce a frequent journey.

### P1 — Incomplete action is shipped as a visible fallback

**Tell:** placeholder product behavior.  
**Where:** `frontend/components/head-nurse/tasks/UnifiedTaskCommandBar.tsx:151`.

**Evidence:** when `onExport` is absent, the button displays “Export feature coming soon”.

**Impact:** the UI advertises a function that is not connected.

**Fix:** hide/disable the control with an explicit reason until an export owner exists, or implement the action with a RED/GREEN E2E guarantee. Do not ship a clickable no-op.

### P1 — Legacy and new operational surfaces overlap

**Tell:** multiple hubs for the same task/workflow domain.  
**Where:**

- `frontend/components/workflow/OperationsConsole.tsx:681-2899`
- `frontend/components/workflow/WorkflowTasksHubContent.tsx`
- Head Nurse and Supervisor task pages/components.

**Impact:** users and maintainers cannot identify the canonical workflow owner; fixes can land in one surface and not another.

**Fix:** choose one Tasks/Work route and one shared domain component. Keep old routes as redirects during cutover; delete obsolete implementations only after route and E2E evidence.

### P2 — Language and product tone drift

**Tell:** untranslated hard-coded strings in otherwise localized screens.  
**Where:** `frontend/app/admin/demo-control/page.tsx` defaults such as “Manual Test Alert”, “Triggered from Manual Testing Panel”, “Ready”, “Select actor”, and “Select room”; Supervisor prescription form also contains hard-coded English placeholders.

**Impact:** Thai/English switching is incomplete and simulator copy feels like a developer panel rather than a production-grade testing environment.

**Fix:** move user-visible strings to i18n; use clinical/test vocabulary consistent with `PRODUCT.md` and `DESIGN.md`.

## Canonical user journeys for Phase 2

1. **Start shift:** As a Supervisor, I see the highest-risk unresolved items and staffing exceptions before secondary metrics.
2. **Respond to emergency:** I acknowledge, assign, open patient context, and record resolution without jumping between duplicate queues.
3. **Manage work:** I assign/reassign/complete tasks and see one consistent state in dashboard, task list, and handover.
4. **Manage ward:** I access patients, staff, schedules, devices, floorplans, and messages through one predictable navigation model.
5. **Use AI intentionally:** I can distinguish “Ask EaseAI” from navigation and clinical mutations before clicking.
6. **Test safely:** As an Admin in simulator mode, I can inject deterministic scenarios; all role screens render through the same contracts with a persistent Simulation indicator.
7. **Operate production safely:** In production mode, no simulator reset, generated sample, probability, or scenario-control action is available.
8. **Use embedded WheelSense:** I navigate WheelSense-specific LVGL screens on hardware or desktop simulator through the same UI state contract.
